`docs/move-notation.md` та `docs/move-validation.md`, плюс дві знахідки

незаповнений фасад рушія). Обидва вихідні документи лишаються джерелом
дизайн-рішень — тут лише впорядкований, пріоритезований план **дій**, без
повторення обґрунтувань, які вже є там.

## 1. Мета документа

Дати відповідь на питання "що робити далі й у якому порядку" — без
необхідності тримати в голові весь контекст обох design-doc одночасно.
Кожен крок нижче: (а) посилається на розділ-джерело дизайну, якщо він є,
(б) дає конкретний список файлів для зміни, (в) визначає критерій "готово".

## 3. Пріоритезація

1. **`localStorage`** — єдиний пункт із реальним ризиком (втрата сумісності
   при майбутній зміні схеми `history`, запис на кожен тік годинника).
   Дизайн повністю готовий, лишається лише реалізація.
2. **Прибрати debug-логи** — дешево, нуль архітектурного ризику, підвищує
   якість коду перед тим, як чіпати `gameOperations.js`/`store.js` далі.
3. **Фасад `engine/index.js`** — консолідація перед тим, як додавати щось
   нове до рушія (perft, нічиї) — інакше нове теж піде "в обхід" фасаду.
4. **Perft-тест** — дешевий, ловить приховані баги в уже написаному рушії.
5. **PGN-експорт** — продуктова фіча, нічого не блокує і не блокується.
6. **Undo / перегляд історії** — найдорожчий пункт (нова модель даних,
   UI-режим перегляду), робити після PGN.
7. **Нічиї** — найнижчий пріоритет, ізольований від решти.

### Крок 1 — `localStorage` зі схемою версій ⬜

Джерело дизайну: `move-notation.md`, розділ 9 (код уже написаний там,
лишається перенести).

Файли: `src/redux/store.js` (переписати), новий `src/redux/persistGame.js`
(виокремити логіку зі `store.js`, щоб її можна було тестувати без Redux).

1. `src/redux/persistGame.js`:
   ```js
   export const STORAGE_KEY = 'chessb:v1:game';
   export const SCHEMA_VERSION = 1;

   export function savePersistedGame(gameState) {
     try {
       const payload = { version: SCHEMA_VERSION, savedAt: Date.now(), state: gameState };
       localStorage.setItem(STORAGE_KEY, JSON.stringify(payload));
     } catch (err) {
       console.error('Не вдалося зберегти стан:', err);
     }
   }

   export function loadPersistedGame() {
     try {
       const raw = localStorage.getItem(STORAGE_KEY);
       if (!raw) return undefined;
       const payload = JSON.parse(raw);
       if (payload.version !== SCHEMA_VERSION) return undefined;
       return payload.state;
     } catch {
       return undefined;
     }
   }
   ```
2. `store.js`: викликати `loadPersistedGame()` як `preloadedState.game` при
   створенні store; підписатись на `savePersistedGame` замість інлайн-логіки.
3. Розділити частоту запису:
   - миттєвий виклик `savePersistedGame` на `moveExecuted`/`endGame`
     (найпростіше: невеликий middleware, що перевіряє `action.type`, замість
     `store.subscribe` на кожен dispatch);
   - `updateTime` (тік годинника) — throttle ~5с, або взагалі не писати
     щосекунди (час відновлюється достатньо точно і без цього).
4. На старті додатку (`main.jsx` або `HomePage`) — якщо `loadPersistedGame()`
   повернув стан, використати його замість дефолтного; інакше почати нову
   партію (без крашу).

Тести: `src/redux/persistGame.test.js` — збереження/читання, неправильна
версія схеми → `undefined`, пошкоджений JSON → `undefined` (не кидає),
`localStorage` недоступний (приватний режим) → не кидає.

**Готово, коли:** перезавантаження сторінки посеред партії відновлює дошку,
історію ходів і час; зміна `SCHEMA_VERSION` в коді симулює несумісність і
не ламає застосунок (просто починає нову партію).

### Крок 4 — Perft-тест ⬜

Джерело дизайну: `move-validation.md`, розділ 6 (останній абзац), розділ 7 п.4.

Файл: `src/engine/perft.test.js` (новий).

1. Написати `perft(gameState, depth)` — рекурсивний підрахунок вузлів
   дерева ходів через уже готовий `getAllLegalMoves`:
   ```js
   function perft(state, depth) {
     if (depth === 0) return 1;
     const moves = getAllLegalMoves(state, currentColor(state));
     if (depth === 1) return moves.length;
     return moves.reduce((sum, move) => sum + perft(applyMove(state, move), depth - 1), 0);
   }
   ```
   (`applyMove` — можливо, доведеться написати як чисту функцію в
   `engine/`, якщо її ще немає окремо від Redux-редюсера — перевірити,
   чи можна перевикористати щось із `legalMoves.js`/`gameStatus.js`, перш
   ніж писати нову).
2. Звірити зі стартової позиції з еталонними числами:
   `perft(1)=20, perft(2)=400, perft(3)=8902, perft(4)=197281`.
3. Якщо є час/потреба — додати 1-2 відомі "тестові" FEN-позиції
   (наприклад, Kiwipete) з опублікованими eталонними числами для глибшої
   перевірки рокіровки/en passant у комбінації.

**Готово, коли:** `perft(1..4)` від стартової позиції збігається з

### Крок 6 — Undo / перегляд історії ходів ⬜

Дизайн: `move-notation.md`, розділ 11. Найдорожчий пункт — вимагає зміни
моделі даних, тому розбитий на під-кроки.

1. **Додати `fenAfter` в елемент `history`.** Зміна в
   `gameSlice.js:moveExecuted` — після застосування ходу серіалізувати
   `state.board` у FEN (є вже `fenConverter.js` у проєкті — перевірити, чи
   покриває напрямок `board → FEN`, чи лише `FEN → board`; можливо,
   доведеться дописати зворотну функцію).
   - **Ризик:** це зміна форми `history`, яка вплине на всі 139 тестів, що
     звіряють точну форму об'єкта. Робити окремим комітом, прогнати повний
     `npm run test` одразу після.
   - **Сумісність зі збереженими партіями (крок 1):** старі записи в
     `localStorage` не матимуть `fenAfter` — саме для цього призначена
     `SCHEMA_VERSION` (крок 1, п.3): підняти версію на 2 разом із цією
     зміною, щоб старі збереження коректно ігнорувались, а не падали.
2. **Read-only перегляд позиції** (простіший сценарій, робити першим):
   клік по ходу в `MoveList` → показати `fenAfter` цього ходу на дошці в
   окремому "viewing mode" (прапорець у `gameSlice`, наприклад
   `viewingPly: number | null`), не чіпаючи `board`/`plyCount`. Вихід із
   режиму — клік на "поточну позицію"/останній хід.
3. **Справжній undo** (обрізання `history`, відновлення `board`,
   коригування `plyCount` і часу) — окреме продуктове рішення: чи взагалі
   потрібен undo в грі з таймером. **Не починати без явного підтвердження
   від користувача**, що ця фіча потрібна — на відміну від інших кроків
   цього плану, тут є відкрите продуктове питання, не лише технічне.

**Готово (для read-only перегляду), коли:** клік по будь-якому ходу в
списку показує відповідну позицію на дошці; повернення до "живої" гри
не втрачає стан.
