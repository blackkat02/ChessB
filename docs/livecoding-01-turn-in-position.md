Дата: 2026-11-03. Тренування live coding на реальному коді проєкту.
Обсяг — пів кроку: підкрок 4.1 з `docs/layer-separation-step4.md`, але

## Формат

- **45 хвилин**, таймер видимий.
- **Думаєш уголос.** Ментор (або запис екрана) чує, що ти робиш і чому.
  Мовчазні 5 хвилин — гірше, ніж неправильна ідея, сказана вголос.
- **Тест спершу.** Кожна зміна поведінки починається з червоного тесту.
- Можна: документація MDN / Redux Toolkit / Vitest, власний код проєкту.
  Не можна: AI-асистенти, готові розв'язки з `layer-separation-step4.md`.
- Комітиш маленькими кроками. Наприкінці — 2–4 коміти, а не один.

Старт:

```sh
git switch -c live/turn-in-position
npm test        # переконайся, що все зелене ДО початку
```

## Умова (читається вголос на старті)

> Зараз черга ходу обчислюється з кількості зроблених напівходів:
> `selectCurrentTurn = plyCount % 2 === 0 ? 'w' : 'b'`. Через це рушій
> не знає, хто ходить, а партія з позиції, де першими ходять чорні,
> неможлива.
>
> Зроби `turn` частиною позиції: `{ board, castlingRights,
> enPassantTarget, turn }`. Після будь-якого ходу `turn` має перемикатися
> на суперника того, хто ходив. Редюсер нічого не обчислює — лише записує.
> `selectCurrentTurn` має читати `turn` зі стану, а не з `plyCount`.
>
> Поведінка гри для гравця не змінюється. Стан поки лишається в одному
> слайсі `state.game` — розбиття на слайси не входить у задачу.

## Критерії приймання

1. `applyMove(position, move).position.turn` — колір суперника того, хто
   ходив. Колір береться **з фігури**, не з `position.turn`.
2. Вхідна позиція `applyMove` не змінюється (існуючий тест на це має лишитися
   зеленим).
3. `state.game.turn` існує, на старті партії — `'w'`, після ходу — те, що
   прийшло в `payload.position.turn`.
4. `selectCurrentTurn` не використовує `plyCount`.
5. `selectPosition` повертає `turn`.
6. `npm test` і `npm run lint` зелені. Жоден тест не видалено.
7. Ти можеш пояснити, що станеться з партією, збереженою в `localStorage`
   до твоєї зміни, і що ти з цим зробив.

## Для ментора

Розділ нижче кандидат не читає до кінця сесії.

<details>
<summary>Ключ: що має змінитися</summary>

- `applyMove.js`: у поверненій позиції `turn: getOpponentColor(getPieceColor(piece))`;
  JSDoc контракту оновлено.
- `applyMove.test.js`: 2 нові тести (хід білих → `'b'`, хід чорних → `'w'`).
- `src/test/fixtures/state.js`: `makeGameState` — `turn: 'w'` за
  замовчуванням; `makeMovePayload` — `position.turn: 'b'`.
- `gameSlice.js`: `initialState.turn = COLORS.WHITE`; у `moveExecuted`
  `state.turn = position.turn`. `newGameStarted` скидає через `initialState`
  — окремо чіпати не треба (перевір, що кандидат це помітив, а не дописав).
- `gameSelectors.js`: `selectCurrentTurn = (state) => state.game.turn`;
  `selectPosition` з `turn`; коментар «turn — похідне значення» прибраний.

</details>

<details>
<summary>Ключ: які тести впадуть і чому</summary>

Ті, де черга чорних задавалась через `plyCount: 1` і від черги щось
залежить:

| Файл | Тест | Чому |
|---|---|---|
| `gameOperations.test.js` | промоція чорного пішака; мат `Ra1#`; хід в аналізі після мату (мат там ставлять чорні) | `attemptMove` відкидає хід «не за чергою»: `turn` тепер `'w'` з `initialState` |
| `gameSelectors.test.js` | `selectClockRemaining` | активна сторона визначається через `selectCurrentTurn` |
| `store.test.jsx` | відновлення з годинником чорних (`// непарне — хід чорних`) | те саме, плюс збережений стан без `turn` |

Тести з `plyCount: 1`, які **не** падають, і чому — добрий матеріал для
розмови:

- `gameSlice.test.js`: редюсер не дивиться на чергу, годинник обирається за
  `payload.color`.
- `useGameState.test.jsx` («gameState віддає whiteTime/blackTime/turnStartedAt
  БЕЗ обчислень»): перевіряє лише сирі значення годинників, черга не бере
  участі.

Якщо кандидат «на всяк випадок» правитиме їх — питання: навіщо?

Правильне виправлення — додати `turn: 'b'` у стан тесту, **не** прибирати
`plyCount: 1`: обидва поля тепер означають різне, і тест має задавати обидва.

</details>

<details>
<summary>Ключ: persist</summary>

Збережений стан версії 3 не має `turn` → `selectCurrentTurn` повертає
`undefined` → жодна сторона не може ходити, годинники не йдуть. Тести
цього не ловлять, якщо в них явно заданий `turn`.

Два прийнятні рішення:

1. **Підняти `SCHEMA_VERSION` до 4** — старі збереження ігноруються, гравець
   один раз втрачає незакінчену партію. Просто, узгоджено з планом кроку 4.
2. **Міграція при завантаженні:** `turn ?? (plyCount % 2 === 0 ? 'w' : 'b')`
   для версії 3. Зберігає партії, але додає код, який живе вічно.

Добра відповідь — будь-яке з двох з обґрунтуванням. Погана — не помітити.
Найкраща — помітити, обрати 1, бо крок 4 однаково підніме версію, і сказати
це вголос.

</details>

<details>
<summary>Рубрика оцінювання</summary>

| | 1 — слабко | 2 — норм | 3 — сильно |
|---|---|---|---|
| **Комунікація** | мовчить, пояснює лише після питань | коментує дії | спершу план, потім дії; каже «не знаю, перевіряю ось так» |
| **Тести** | пише код, тести потім або ніколи | тест і код поруч | червоний тест перед кожною зміною поведінки |
| **Діагностика** | правит червоні тести, поки не стануть зеленими | читає повідомлення помилки | пояснює **причину** падіння до правки |
| **Обсяг** | розповзається (розбиває слайси, рефакторить сусідній код) | робить задачу | робить задачу і явно називає, що свідомо не робить |
| **Git** | один коміт наприкінці | кілька комітів | коміти по зелених кроках з осмисленими назвами |
| **Persist** | не помічено | помічено після підказки 4 | помічено самостійно, рішення обґрунтоване |

Червоні прапорці: видалений або закоментований тест; `plyCount` прибраний з
тестів замість додавання `turn`; `turn` обчислюється в редюсері
(`getOpponentColor` у `gameSlice.js`); колір у `applyMove` береться з
`position.turn` (зламає режим аналізу).

</details>
